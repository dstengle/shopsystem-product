# Initiative: Process runner

## Framing

Originator (product authority, 2026-09-07, through the lead shop's operational contract, which has no artifact yet (lead-4kymc); req-2026-09-07-run-efficiency, section 1): "The lead-pm should not be coordinating a running graph at all, not just the bookkeeping. This should be a deterministic process that can be run by a very cheap and fast model." "converge, but make process runner first"

Problem: the process definitions draw the flow as runtime, agent, and human steps, but nothing runs them; the lead-pm runs them by hand in one long context. Outcome: a process definition runs itself — runtime steps as written, agent steps with their declared inputs only, human steps waiting for the human — and whoever moves the run carries only the step it is on.

## For whom

The lead-pm, who stops coordinating; every role, which receives only its inputs. Measure: context tokens processed by whoever moves the run, per delivered feature. Now: 32M — 64M over the two features of init-tool-skills. Target: under 1M. Interaction types: command line.

## Appetite

One working session of the lead shop: one process run end to end by the runner the bet chooses, with the run's context measured. The authority's direction, 2026-09-07: "I would like to avoid the expense of a code implementation for now and just get a cheap model to do what the lead-pm has been doing to coordinate and do bookkeeping." No-gos, each with its reason: no code runner — the authority's direction above, and the migration question (req-2026-09-06-migration-review) decides later whether one is a lead-shop tool or the shopsystem engine; no change to a process definition beyond what a run needs — the definitions are approved and the run is their proof, not their rewrite.

## Feasibility and usability

Feasible on the stack as it stands: the harness runs a role from its
rendered definition and admits a model per role; the definitions are
the program, unchanged; every part sits in the lead shop's tree. Decision the bet depends on: the runner is a defined
role, restartable at any step from the run's anchor (the work item
the run is recorded on), no code runner — adr-2026-09-07-coordinator-role,
checked. Risks: an agent that cannot launch agents; a cheap model
reading a condition; outputs returned as prose. Full offer: history
v3. (architect, 2026-09-07)

Usability: a hypothesis. The command line named in For whom is the
corpus's assistant type — a model acting on what the person says —
and the command-line rules hold for the shell commands its runtime
steps run. The person starts, holds, resumes, cancels, and answers a
run there in one turn each; an ask shows its question and default;
cancel and a default taken are confirmed first. Evidence: the first
coordinated run, each human turn counted. Full offer: history v4.
(designer, 2026-09-07)

## Decomposition

None: no Bounded Context is touched — the runner role, its rendering,
and any compiler change sit in the lead shop's tree; no contract
exists on this branch. Cross-context flow: none.
