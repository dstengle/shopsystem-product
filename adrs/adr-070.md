## Context

The knowledge system *validates* artifacts (per-file `shop-knowledge validate`
plus the corpus coherence gate) but nothing *guides* their creation. The result
is repeated lifecycle-jumping: freehand decision docs with no provenance, wrong
starting `status`, the withdrawn ADR-067/PDR-035-draft, and a lead-pm ADR misstep
on 2026-07-25 caught only by the product authority. pdr-038 (this slice's needs)
decides that **every one of the eight kinds gets a writing skill** that bundles
its template and schema checks and walks the author through the kind's lifecycle,
and that the skills **reuse the single-sourced template/schema, never copy them**.
This ADR is the **skill-template structure** half of slice #4: the common
structure every per-kind writing skill follows so the eight are consistent and
generatable. The **enforcement** half — shop-templates blocking that every kind
has a valid writing skill — is adr-071, which builds on this structure.

This ADR states the skill *structure* at schema/mechanism altitude — what
sections a writing skill carries, what it references, and what it walks the author
through. It writes no skill prose body and no generator/CLI code; those are
downstream shopsystem-templates work named for the acceptance queue.

### Pre-state empirical findings (artifact surface, ADR-018 D1/D2)

Verified from the lead CWD against this repo's `adrs/`/`pdrs/` records, the
installed `shop-templates` / `shop-knowledge` / `shop-knowledge-gate` tooling, and
the live `.claude/skills/` tree. No BC source on this host (ADR-018); "empirical"
is the contract/artifact surface.

1. **Skills are Claude Code skill directories: `SKILL.md` + optional resources,
   progressive-disclosure. CONFIRMED** (`find .claude/skills`). Each skill is a
   directory whose `SKILL.md` carries a two-field frontmatter (`name`,
   `description`) — the `description` is the progressive-disclosure trigger the
   agent selects on — followed by a prose procedure. Skills may carry sibling
   resource files; most current skills are `SKILL.md`-only. A `.provenance` marker
   records `CANONICAL` vs `LOCAL` (canonical skills are poured, not hand-authored
   here).

2. **The canonical skill tree is POURED by shop-templates, not authored per
   repo. CONFIRMED** (`shop-templates` subcommands `list/show/bootstrap/update`;
   the `create-bc` skill records that `shop-templates bootstrap --shop-type bc …`
   "pours the canonical BC skill tree into `.claude/skills/`"). So shop-templates
   is the pour/render authority for role+skill furniture — the right host for the
   enforcement in adr-071, and the mechanism whose single-source discipline this
   structure must ride rather than fork.

3. **The kind set and its single source. CONFIRMED** (`shop-knowledge template
   <kind>` succeeds for all eight: adr, pdr, brief, intent-record, candidate,
   session-record, current-state, prioritization-record). Each kind's template
   (`shop-knowledge template <kind>`) and schema (`shop-knowledge schema <kind>`)
   are **generated read-only from the kind's per-type typedef** — the ADR-059
   typedef→generator single source carried forward by ADR-067 D1. `shop-knowledge
   schema adr` reports the kind's `required_sections`, `statuses`,
   `non_empty_fields`, and `type_required_fields` — exactly the lifecycle facts a
   writing skill must walk the author through, already machine-readable from the
   single source.

4. **No per-kind writing skill exists today. CONFIRMED** (`ls .claude/skills` —
   no `write-*`/authoring skill; the present skills are the PM discovery/technique
   set). So this is **net-new capability**: there is no writing-skill structure to
   tighten, and adr-071's enforcement of "every kind has one" starts from zero
   coverage.

5. **`@scenario_hash` retirement enumeration. CONFIRMED — empty.** This is a
   skill-structure/mechanism decision. Enumerated the lead-held corpus
   (`grep -r "@scenario_hash" features/` over this repo's `features/` tree, the
   authoritative lead-side surface per ADR-018) — no Gherkin pins a per-kind
   writing-skill structure, so no BC-side `@scenario_hash` is retired, superseded,
   or contradicted by this landing (ADR-064 retirement convention: nothing to
   retire). The scenario/gate consequences are downstream BC work named for the
   acceptance queue, not dispatched here.

### Options considered

- **Option A — one writing skill parameterized by kind.** A single `write-artifact`
  skill that takes the kind as a parameter. Rejected: progressive disclosure
  selects a skill by its `description` trigger (finding 1); one skill's single
  description cannot present a precise per-kind trigger ("I am writing an ADR" vs
  "…a candidate"), so the author gets a generic prompt and the mis-selection risk
  the writing skills exist to remove creeps back. Enforcement "every recognized
  kind has a writing skill" (adr-071) also loses its natural per-kind presence
  check — one skill either exists or does not, coverage-per-kind is no longer
  observable.
- **Option B — eight discrete hand-authored writing skills.** Rejected: eight
  hand-copied skills drift from each other and from the typedef — the exact
  copy-drift failure the ADR-059 single source exists to prevent, and the failure
  pdr-038/cand-009 name as the whole point of "reuse, never copy."
- **Option C — eight discrete writing skills GENERATED from one common structure
  single-sourced from the typedef (CHOSEN).** One skill-template structure (this
  ADR), materialized as eight discrete per-kind skill directories by the same
  typedef→generator single source ADR-059/ADR-067 already bless. Discrete (so each
  carries a precise per-kind progressive-disclosure trigger and per-kind
  enforceable presence) AND consistent (so the eight cannot drift — they are
  generated read-only from the common structure plus each kind's typedef, and
  drift-gated the same way templates/schemas are).

## Decision

Every per-kind writing skill follows **one common structure**, and the eight are
**generated** from that structure plus each kind's per-type typedef — the same
ADR-059 typedef→generator single source that already emits the kind's template and
schema (finding 3, ADR-067 D1). A writing skill **reuses the single-sourced
template/schema by CLI reference and never embeds a frozen copy** (a copy drifts;
reuse is the whole point, cand-009/pdr-038). This ADR states the structure at
schema/mechanism altitude only — no skill prose body, no generator code.

### D1 — A per-kind writing skill is a Claude Code skill directory, one per kind

Each of the eight kinds gets its **own discrete** writing-skill directory
(`.claude/skills/write-<kind>/`), a `SKILL.md` plus optional resources under the
existing progressive-disclosure convention (finding 1). Eight discrete skills —
**not** one kind-parameterized skill (Option A) — so each carries a precise
per-kind trigger and adr-071's enforcement has a per-kind presence check to make.
The `.provenance` marker is `CANONICAL`: these are poured by shop-templates
(finding 2), not hand-authored per repo.

### D2 — Generated from one common structure, single-sourced from the typedef

The eight are **generated read-only** from the common structure below plus each
kind's per-type typedef — the same single source (ADR-059, carried by ADR-067 D1)
that emits `shop-knowledge template <kind>` and `schema <kind>`. This is what makes
Option C's discreteness safe: the eight cannot drift from each other or from the
typedef because none is hand-copied — each is regenerated from the common
structure and the kind's typedef, and is subject to the same `--check` drift gate
that guards the generated template/schema. The lifecycle facts the skill walks
(required sections, status enum, edge participation) are **read from the kind's
typedef at generation time** (finding 3), not transcribed by hand.

### D3 — Common structure: five required parts

Every generated per-kind writing skill carries these five parts:

1. **Frontmatter trigger.** `name: write-<kind>` and a per-kind `description` that
   is the progressive-disclosure trigger for "the author is creating a `<kind>`"
   (finding 1). The description is per-kind so selection is precise (D1).
2. **Template-fetch part.** Directs the author to obtain the kind's shape from the
   **live** template via `shop-knowledge template <kind>` — a **reference to the
   single source**, never an embedded copy of the template body (D2, reuse
   discipline). The skill names the command; it does not inline the template.
3. **Schema-check part.** Directs the author to validate the drafted file with
   `shop-knowledge validate <path>` and names the kind's schema surface via
   `shop-knowledge schema <kind>` (its `required_sections`, `statuses`,
   `non_empty_fields`) as the check the author's draft must pass — again by
   reference, not by embedding a frozen schema.
4. **Lifecycle walk.** Walks the author through the kind's lifecycle as adr-069
   specifies it for that kind (the **check target**): the **correct starting
   `status`** (the first value of the kind's status enum — e.g. adr→`proposed`,
   pdr→`proposed`, brief→`draft`, intent-record→`recorded`, candidate→`exploring`,
   session-record→`open`, prioritization-record→`draft`, current-state→`current`
   per adr-069 D1–D8); the **provenance edges to set** (the kind's `derives-from`
   participation and requiredness per adr-069's per-kind edge participation — e.g.
   adr requires `derives-from` non-empty, intent-record is the provenance head and
   sets none); and the **required sections** the author must fill (the kind's
   `required_sections` per adr-069 / `shop-knowledge schema <kind>`).
5. **Reuse-discipline note.** States explicitly that the template and schema are
   **referenced live, never copied** — a writing skill that embeds a frozen
   template/schema body is a defect (it re-installs the drift ADR-059 eliminated).

### D4 — Reuse-not-copy is the structural invariant adr-071 checks

The load-bearing invariant is that a writing skill's authority points at the
**live** `shop-knowledge template`/`schema`/`validate` surface (D3 parts 2–3, 5),
so a typedef change flows into the skill's guidance without a second edit. This
invariant is exactly what adr-071's validity check enforces (a skill that embeds a
frozen copy, or omits a required section for its kind, fails). This ADR defines the
structure; adr-071 makes "every kind has one and each is valid" blocking.

## Consequences

- **Authoring is guided at creation time** by a per-kind skill that hands the
  author the live template, the schema check, and the kind's lifecycle — the
  counterpart to the coherence gate, closing the authoring-guidance gap pdr-038
  names, rather than catching jumps after the fact.
- **The eight are consistent and generatable** (D2/D3): one common structure plus
  each kind's typedef generates all eight read-only, so they cannot drift from each
  other or from the single source — Option C keeps discreteness without the copy
  drift of Option B.
- **Reuse-not-copy is structural** (D4): the skills reference the live
  template/schema surface; no second copy of any template or schema is introduced,
  honoring cand-009/intent-011's failure condition directly.
- **On acceptance, a dispatch to shopsystem-templates is implied — named here, NOT
  dispatched.** shopsystem-templates owns the skill-pour/render discipline
  (finding 2), so it realizes this structure: the generator that emits the eight
  per-kind writing skills read-only from the common structure plus each kind's
  typedef, poured into `.claude/skills/write-<kind>/`. The writing skills **reuse**
  the shopsystem-knowledge `template`/`schema`/`validate` surface (finding 3); no
  second copy is created. The message-type discriminator is run at dispatch time
  against shopsystem-templates' then-current pre-state (a `request_bugfix`
  tightening for pour/render behavior already generated; `assign_scenarios` for the
  net-new writing-skill generation no scenario pins today, finding 5) — flagged for
  the acceptance queue, not selected here.
- **No supersession edge while proposed.** New capability — this ADR supersedes
  nothing; its `derives-from` runs to `adr-069` (the per-kind schema check target)
  and `pdr-038` (the needs), both of which exist, so the provenance gate is
  satisfied. The paired enforcement mechanism is adr-071 (`derives-from: adr-070`).

### Open design forks for the acceptance review (product authority)

1. **One skill parameterized by kind vs eight discrete skills** (Options A/C).
   **Decided here: eight discrete skills, generated from one common structure**
   (D1/D2). Rationale: precise per-kind progressive-disclosure trigger and a
   per-kind enforceable presence check, with drift prevented by generation rather
   than by collapsing to one skill. Alternative (one parameterized skill) remains
   the authority's call; flagged.
2. **Consult-decision-index coupling** (lead-x7bp lineage; intent-011/cand-009 open
   thread). **Recommendation: keep OUT of the baked mechanism** — the structure
   here bundles only template + schema-check + lifecycle walk. Injecting relevant
   accepted-decision context at authoring time is a **separate capability** (a
   runtime dependency on the decision index, orthogonal to the reuse-not-copy
   template/schema discipline) and would expand the moderate appetite. Flagged as a
   **follow-on option**, not baked in.
3. **Writing-skill body altitude — resources vs single SKILL.md** (finding 1). Not
   decided here (this ADR is structure, not prose): whether the lifecycle walk
   lives inline in `SKILL.md` or in a progressive-disclosure resource file is a
   realization choice for the shopsystem-templates dispatch. Flagged.
