## Context

`cand-010` shaped corpus entry-point finding as a composable, tag-based skill
set and left one rabbit hole explicitly to the Architect: **the tag write path
and gate acceptance** — whether tags are written by a dedicated corpus command
or by a frontmatter edit revalidated through the coherence gate. `brief-025`
committed that candidate, carried the product authority's evidence-first build
sequence verbatim as its work-split, assembled the evidence for the write-path
question **without a recommendation**, and flagged a third consideration the
rabbit hole had not named — that no generated `shop-knowledge template <kind>`
emits a `tags:` key and `shop-knowledge schema <kind>` does not report the field,
so the write surface makes tags invisible to every authoring path. Placing that
consideration was also handed to the Architect.

This ADR answers both. It resolves **before** `brief-025` step 2's scenarios are
authored; it does not gate step 1 and it does not gate the brief.

### Pre-state empirical findings (artifact surface, ADR-018 D1/D2)

Verified from the lead CWD against the contract/artifact surface only: the
installed `shop-knowledge` / `shop-knowledge-gate` / `scenarios` CLIs, this
repo's `features/`, `adrs/`, `pdrs/`, `briefs/`, `candidates/`. **No BC source is
on this host and none was read, run, or git-observed** (ADR-018 D1). The
installed CLIs are *contract tools* (ADR-018 D2) — invoking them over corpus text
returns a contract fact. **Every exit code below was measured unpiped**
(`out=$(cmd 2>&1); rc=$?`), because `$?` after a pipe reports the pipe's status,
not the CLI's.

1. **`shop-knowledge` exposes exactly six verbs and has no write verb.
   CONFIRMED.** Bare invocation returns
   `error: a subcommand is required (template, schema, validate, navigate,
   render, query)` and **exits 2**. Shape (i) is therefore net-new BC capability;
   shape (ii) uses only surfaces that exist.

2. **The ENTIRE installed knowledge surface is non-mutating, and the gate's own
   pinned contract is report-with-remediation, not write. CONFIRMED.**
   `shop-knowledge-gate --help` returns
   `usage: shop-knowledge-gate [-h] [--mode {authoring,distribution}] root` —
   there is **no** `--fix` / `--apply` / write mode; the only option is the
   advisory-vs-blocking mode selector. ADR-067 D2's phrase "the gate
   **materializes and maintains** both directions" is realized as *reporting*:
   `features/shopsystem-knowledge/base_schema_materialized_edges.feature:26` and
   `features/shopsystem-knowledge/coherence_gate_typed_edges.feature:30` both pin
   that the finding "carries its check-id and **a remediation to write** the
   back-edge on B". **The gate names the write; the author performs it.** So
   `template`/`schema` emit, `validate` reports, the gate reports, and
   `navigate`/`render`/`query` read — no installed knowledge surface mutates an
   artifact.

3. **The frontmatter-edit path already works END TO END. CONFIRMED by
   construction.** On a copy of this repo's live 167-artifact corpus (scratchpad,
   `rsync -a --exclude=.git`), a `tags: [corpus-read, tagging,
   entry-point-finding]` line was added by hand to `adrs/adr-068.md`'s
   frontmatter. Then:
   - `shop-knowledge validate <path>` → `conforming: <path>`, **exit 0**;
   - `shop-knowledge query --corpus <root> --facet tag --value corpus-read` →
     `[{"id": "adr-068", ...}]`, **exit 0** (and `--value tagging` likewise;
     `--value nope` → `[]`, exit 0);
   - `shop-knowledge-gate .` → `no coherence findings` /
     `aggregate verdict: exit 0 (mode authoring)`, **exit 0**.

   A hand-written `tags` list is thus accepted by validation, **indexed by the
   live `tag` facet**, and leaves the gate green. Shape (ii) delivers the whole
   step-2 capability with zero net-new BC behavior.

4. **The precedent is already in the live corpus, on the SAME base schema.
   CONFIRMED.** `adrs/adr-059.md` carries `superseded-by: [adr-067]` in
   frontmatter; `shop-knowledge navigate adr-067 --corpus .` resolves it
   (`{"link_field": "supersedes", "target": "adr-059", "resolved": true, ...}`,
   exit 0) and the gate symmetry-checks it. That materialized back-edge — an
   ADR-067 D2 base-schema field, sibling to ADR-067 D4's `tags` — **was written
   by a frontmatter edit**, because no write verb has ever existed. The corpus is
   already authored the way shape (ii) proposes to write tags.

5. **`shop-knowledge validate` is PERMISSIVE to unrecognized frontmatter keys —
   the one real cost of the edit path. CONFIRMED.** Adding
   `zzz-not-a-real-field: [bogus]` to `adrs/adr-067.md` on the scratch copy still
   returns `conforming`, **exit 0**. So validation will **not** catch a
   misspelled or miscased key (`tag:`, `Tags:`) — the document would validate,
   pass the gate, and be silently unfindable. By contrast the **facet name is
   closed**: `query --facet bogus` → `error: unknown facet 'bogus'; expected one
   of type, status, tag, distribution`, **exit 2**. The read side is guarded; the
   written key spelling is not. This finding is what D4 exists to close.

6. **The template/typedef gap is REAL, and BROADER than tags. CONFIRMED, all
   eight kinds, unpiped.** No generated `shop-knowledge template <kind>` emits a
   `tags:` key — **and none emits a `distribution:` key either**, though ADR-067
   D5 declares `distribution` **required on every artifact instance**;
   `grep -rl '^distribution:'` over this corpus returns **0 of 167**.
   `shop-knowledge schema <kind>` reports **no optional field at all** for any
   kind — not `tags`, not `distribution`, not `external-references`, and not any
   of the six edge fields; its emitted keys are `document_shape`, `generated`,
   `id_example`, `id_pattern`, `non_empty_fields`, `read_only`,
   `required_sections`, `shared_required_fields`, `statuses`, `type`,
   `type_required_fields`. Meanwhile the **read side DID land** ADR-067's fields:
   `tag` and `distribution` are both recognized `query` facets (finding 5).
   **ADR-067's realization is therefore SPLIT — loader/query yes, typedef/
   generator no** — which is a different, larger finding than "tags is missing
   from the template", and is why D6 places it outside this decision rather than
   folding it in as a tags footnote.

7. **`@scenario_hash` retirement enumeration. CONFIRMED — EMPTY. Nothing is
   retired, superseded, or contradicted.** Enumerated corpus-wide through the
   installed `scenarios` CLI's aggregate command
   (`scenarios validate --aggregate features/ --origin-root adrs --origin-root
   pdrs --origin-root briefs`) over the full `features/` tree — 940 distinct
   `@scenario_hash` values across the tree, 27 feature files under
   `features/shopsystem-knowledge/` — not a hand-scoped single-file grep.
   Specifically:
   - The **read-only invariant is NOT pinned by any scenario hash.** It lives in
     `features/shopsystem-knowledge/corpus_read_cli.feature`'s Feature narrative
     prose (line 25: "All three verbs are read-only — they never mutate an
     artifact or an edge"). That file's 15 scenario hashes pin navigate/render/
     query behavior, none of which this decision touches. So even shape (i) would
     not have *retired* a hash — but it would have contradicted an accepted
     decision (ADR-068 D2) and the narrative that carries it, which is a worse
     posture, not a better one.
   - `base_schema_distribution_and_fields.feature`'s tags pair —
     `@scenario_hash:9cbc6bee113e1f52` ("an artifact carrying a tags list
     conforms") and `@scenario_hash:64bf2fe14d80e4eb` ("an artifact omitting the
     optional tags field still conforms") — is **PRESERVED** by this decision and
     is the invariant D5 binds. Neither is retired.
   - No `@scenario_hash` anywhere in `features/` pins a knowledge-BC write verb,
     because none exists (finding 1).

### Options considered

- **Option A — a dedicated write verb on `shop-knowledge` that sets a document's
  tags (`cand-010` shape (i)). REJECTED.** Three reasons, in order of weight.
  (a) It is **net-new BC capability** (finding 1): PO-authored scenarios, an
  `assign_scenarios` dispatch, and a BC round trip land on the critical path of
  step 2 — to deliver capability finding 3 shows **already exists**. Under
  `brief-025`'s medium, selection-first appetite that is appetite-blowing spend
  for zero marginal capability. (b) It would make `shop-knowledge` a **mutating
  surface for the first time**, against ADR-068 D2's explicitly *hard* read/write
  boundary and against the gate's pinned report-with-remediation posture
  (finding 2) — a structural change to the BC's whole posture, taken as a side
  effect of populating one optional field. (c) It would not even be
  self-sufficient: the CLI carries **no usage text on any verb** (bead
  `lead-wnrvo`), so a seventh verb would arrive undiscoverable and would *still*
  need a loaded skill to carry its invocation inline. The skill is load-bearing
  either way; the verb is not.

- **Option B — a frontmatter edit revalidated through `shop-knowledge validate` +
  `shop-knowledge-gate` (`cand-010` shape (ii)). CHOSEN.** Available today and
  proven end to end (finding 3); consistent with how this corpus's own
  base-schema edge fields are already authored (finding 4); and it is the
  mechanism ADR-070/ADR-071 already settled for artifact authoring generally —
  a skill that edits the file and checks it against the **live**
  `shop-knowledge template`/`schema`/`validate` surface by reference.

- **Option C — extend the coherence gate with a `--fix`/`--apply` mode that
  writes tags. REJECTED.** The same objection as Option A at higher cost: it
  converts the one surface whose *entire pinned contract* is "report a finding
  and name a remediation" (finding 2) into a mutator, and it relocates tag
  authorship from the per-document authoring act ADR-070 owns into a corpus-wide
  gate run, where blast radius and reviewability are both worse.

## Decision

### D1 — Tags are written by a frontmatter edit; `shop-knowledge` acquires no write verb

A document's `tags` are written by **editing its YAML frontmatter** — the same
act by which every other field of the ADR-067 base schema, including the
materialized back-edges, is already authored in this corpus (finding 4).
`shop-knowledge` **gains no write verb**, and the coherence gate **gains no fix
mode**. The installed knowledge surface stays **non-mutating in full**:
`template`/`schema` emit, `validate` reports, the gate reports a finding plus a
remediation, and `navigate`/`render`/`query` read (finding 2). This is the
general convention, not a tags special case: it governs `distribution`,
`external-references`, and the six edge fields identically.

### D2 — The post-write check is the existing two-step, unchanged

After the edit, the writer runs, in order:

1. `shop-knowledge validate <path>` — must report the document **conforming**
   (exit 0); and
2. `shop-knowledge-gate <root>` — must stay at **zero findings**
   (`no coherence findings`, exit 0).

No new validation surface is introduced. This is exactly `brief-025`'s step-2
acceptance, and finding 3 demonstrates it is satisfiable today.

### D3 — The step-2 tagging skill follows ADR-070's reuse discipline but is NOT a per-kind writing skill

The tagging skill is an **authoring** skill and inherits ADR-070 D3/D4's
reuse-not-copy invariant: it references the **live** `shop-knowledge` surface and
embeds **no** frozen template or schema body. It is **not** one of the eight
per-kind `write-<kind>` writing skills and is therefore **outside ADR-071's
coverage and validity checks**, which are keyed to the recognized artifact-kind
set (ADR-071 D1/D2). Recorded explicitly so that a future gate change does not
mistake a tagging skill for a missing or invalid per-kind writing skill, and so
that the tagging skill is not mistakenly generated from the per-kind common
structure.

### D4 — A query read-back is a MANDATORY post-condition of the write

Because `validate` is permissive to unrecognized frontmatter keys (finding 5), a
misspelled or miscased key (`tag:`, `Tags:`) would validate, pass the gate, and
leave the document **silently unfindable** — the exact silent-false-negative
class `cand-010` exists to remove. Validation is therefore **not** a sufficient
check on this write. The write is complete only once

```
shop-knowledge query --corpus <root> --facet tag --value <one written value>
```

**returns the written document's id**. This read-back is a required post-condition
of every tag write and a **required property of `brief-025` step 2's scenarios**
— it is what converts the permissive-validate hole into a deterministic
post-condition. The facet name itself is already guarded (unknown facet → exit 2,
finding 5), so the read-back is the only unguarded link that needs closing.

### D5 — The ADR-067 conformance invariant is preserved exactly

Both states remain conforming and both stay pinned: a document **carrying** a
`tags` list (`@scenario_hash:9cbc6bee113e1f52`) and a document **omitting** the
optional `tags` field (`@scenario_hash:64bf2fe14d80e4eb`). A document with no
tags is left with **no `tags` key at all**; the key's absence is a conforming
state and **must not** be treated as a defect to repair, nor backfilled with an
empty `tags: []` marker. No tag write may make the key's presence mandatory
anywhere.

### D6 — The template/typedef gap is placed as ADJACENT and SEPARATE

The gap named by `brief-025` finding 1 is **adjacent to this question, and a
separate item** — not inside it, and not unrelated to it.

- **Not inside it.** The write path is decided and works with the typedef exactly
  as installed (finding 3): tags were written, validated conforming, queried
  back, and the gate stayed green without touching the generator. Folding the gap
  in would put a BC dispatch on the critical path of a decision that explicitly
  does not gate the brief.
- **Not unrelated.** It is the mechanical root cause of 0/167 population, and it
  re-asserts at scale: every newly authored artifact starts from a template with
  no `tags:` line, so **post-gate full-corpus population would fight a write
  surface that keeps re-emitting untagged documents**. It is a genuine
  prerequisite for corpus-scale population — just not for this bet.
- **Scoped as its own item, at its true size.** The item is **not** "add `tags:`
  to the templates". Per finding 6 it is a **split ADR-067 realization**: the
  read/loader side landed the base-schema fields (`tag` and `distribution` are
  live facets) while the **typedef→generator side landed none of them** — no
  template emits `tags:` or `distribution:`, 0/167 artifacts carry
  `distribution:` though ADR-067 D5 declares it required, and `schema <kind>`
  reports no optional field at all. That is one coherent gap against ADR-067
  D1/D4/D5/D6, and it takes its **own bead** and its **own `request_bugfix`** to
  `shopsystem-knowledge` (the generator already emits templates and schemas from
  the typedef — this tightens an existing, unpinned emission surface rather than
  adding a capability). It is sequenced **before** post-gate full-corpus
  population and **explicitly not before** `brief-025` step 2.

### D7 — This ADR implies no dispatch

Nothing here is dispatched. D1–D5 are satisfied by lead-side skill authoring on
surfaces that already exist; D6 names a separate item for the queue and does not
compose it. The message-type discriminator for the D6 item is run at dispatch
time against `shopsystem-knowledge`'s then-current pre-state.

## Consequences

- **`brief-025` step 2 is unblocked with zero BC round trips.** Its acceptance
  ("the tagging skill writes a document's tags, the written document passes
  `shop-knowledge validate` as conforming, and `shop-knowledge-gate .` stays at
  zero findings") is demonstrably satisfiable today (finding 3), and gains D4's
  read-back as a further required property. The authority-directed build sequence
  is untouched: this feeds step 2, does not gate step 1, does not gate the brief.
- **`shop-knowledge` stays non-mutating, and that is now a recorded convention**
  rather than an accident of what has shipped. The next architect asking "should
  we add a write verb for `distribution` / `external-references` / the
  back-edges?" reads D1 instead of re-deriving it — which is the specific
  re-litigation risk this ADR exists to close, since "add a write command" is the
  obvious-looking answer that `cand-010` itself reached for.
- **A real silent-failure surface is named and countered** (finding 5 / D4).
  `validate` cannot police frontmatter key spelling; the tag write's correctness
  rests on the query read-back. Any future authoring skill that writes an
  *optional* frontmatter field inherits this hazard and should adopt the same
  read-back pattern.
- **A separate ADR-067-realization item is queued** (D6), correctly sized as a
  split realization across tags + distribution + external-references + the schema
  surface's optional-field silence, rather than mis-scoped as a tags-only
  template tweak. Full-corpus population should not proceed past the step-5 gate
  until it is resolved.
- **`brief-025`'s two flagged-but-unabsorbed defects do not bear on this
  decision.** `lead-uypj5` (`render --format json` crashes 167/167 on a
  date-serialization `TypeError`) is irrelevant to the write path, which uses
  `validate`, the gate, and `query` — `query`'s JSON list output is unaffected and
  was exercised in finding 3. `lead-wnrvo` (no usage text on any verb) does not
  impede the edit path, and it counts **against** Option A: a seventh verb would
  ship undiscoverable and would still need a skill to carry its invocation
  (Option A, reason (c)).
- **This ADR is deliberately left untagged.** Tagging it now would put a
  tagged artifact outside `brief-025` step 3's pinned selection and pollute step
  5's recall/precision accounting, which requires tags to be the only changed
  variable. Tag application belongs to step 3.
- **Supersedes nothing.** It rests on ADR-067 (the `tags` field and the base
  schema) and ADR-068 (the read-only boundary it declines to breach), and is
  consistent with ADR-070/ADR-071 (authoring is done by skills against the live
  surface). No prior decision is retired and no `@scenario_hash` is retired,
  superseded, or contradicted (finding 7).
