## Context

PDR-035 (slice #1, proposed) states the artifact system's **founding
requirement** at capability altitude and deliberately names no mechanism: two
views over one corpus — the **current-system view** (the `accepted` set, which
must be self-contained and mutually consistent) and the **transformation view**
(the full graph including superseded docs and the supersede chains) — separated
by the `status` axis, with the changelog as the one sanctioned self-containment
exception. This ADR is **slice #2**: the **base schema** that serves that
requirement. It states *what fields the frontmatter carries and what the
coherence gate enforces*; it does not write generator code, CLI flag names, or
scenarios (those are downstream BC work).

### Pre-state empirical findings (artifact surface, ADR-018 D1/D2)

Verified from the lead CWD against this repo's `adr/`/`pdr/` records and the
installed knowledge tooling (`shop-knowledge schema adr`,
`shop-knowledge-gate`). No BC source on this host (ADR-018).

1. **ADR-059 is the current format mechanism and is `accepted`. CONFIRMED**
   (read of `adrs/adr-059.md`). The shopsystem-knowledge BC single-sources each
   artifact FORMAT from a per-type `typedef/*.yaml`; one generator emits BOTH
   the template (`.md`) and the JSON Schema fragment (`.json`); generated files
   are read-only; a `--check` drift gate fails CI on any hand-edit;
   `x-required-sections` gives the gate a body-structure check. ADR-059's own
   `SHARED_REQUIRED` reconciliation pinned the shared required set to
   `[type, id, title, description, status, created, updated, authors]`.

2. **The current schema materializes only the forward `derives-from` link and
   stores no back-edges. CONFIRMED** (`shop-knowledge schema adr`): the only
   `type_required` / `non_empty` link field is `derives-from`; there is no
   `superseded-by`, `derived-by`, `references`, `referenced-by`, `tags`, or
   `distribution` field in the shared schema. So back-references today are
   *computed transitively* (walk every doc's forward edges to find who points
   here), and the graph is one-directional from any single doc's frontmatter —
   exactly the posture PDR-035's transformation view needs replaced so that
   history is *traversable from frontmatter alone*.

3. **The ADR tier model (ADR-034/035) is an ADR-scoped, informal convention.
   CONFIRMED** (read of `adrs/adr-034.md`, `adrs/adr-035.md`). ADR-035 D1 names
   three tiers — `framework` (applies to every product instantiation),
   `system-global` (cross-BC, *this* product), `bc-local` (one BC's internals,
   living in the BC repo, never on the lead host per ADR-035 D3). ADR-034 D2
   records tier as a lightweight `**Tier:**` header *tag*, "convention, not
   schema — there is no tool that enforces it." The tier axis's top split —
   `framework` vs. the product tiers — forces the "framework or product?"
   question, which is *unanswerable for this repo* because the product IS the
   framework. The `distribution` field this ADR introduces **replaces that tier
   model wholesale** (see D5) with a within-product SCOPE axis that is always
   answerable, generalized from ADRs to all eight artifact kinds; so ADR-034 and
   ADR-035 are *retired/superseded* by this ADR (D5/D8), not reconciled with it.

4. **`@scenario_hash` retirement enumeration. CONFIRMED — empty.** This is a
   schema/mechanism decision; no lead-held Gherkin pins the artifact-frontmatter
   format, and no BC-side `@scenario_hash` is retired, superseded, or
   contradicted by *this* landing. The scenario-register consequences are
   downstream BC work named for the acceptance queue (Consequences), not
   dispatched here.

### Options considered

- **Option A — Compute back-edges transitively; do not store them (status quo,
  finding 2).** Keep only forward `derives-from`; derive `superseded-by` /
  `referenced-by` by scanning the corpus. Rejected: the transformation view
  then requires a full-corpus scan to answer "what superseded this?", so history
  is not traversable from a single doc's frontmatter; and there is no place for
  the gate to *fail on asymmetry*, because there is only one stored direction to
  check. PDR-035's requirement that history be reachable from the frontmatter
  graph is unmet.
- **Option B — Materialize both directions of the three edge pairs in
  frontmatter; the gate maintains them and fails on asymmetry (CHOSEN).** Both
  the forward edge and its back-edge are stored; the graph is traversable from
  any doc alone; the gate's symmetry check makes a dangling half-edge a hard
  failure rather than a silent inconsistency.
- **Option C — Fold the new fields into a hand-authored schema, abandoning
  ADR-059's typedef→generator single source.** Rejected: re-installs the exact
  template↔schema drift ADR-059 eliminated by construction. The base schema must
  be carried by the same single-source mechanism, not authored twice.

## Decision

The artifact-system **base schema** is the shared frontmatter contract every
one of the eight artifact kinds carries, single-sourced and drift-gated by
ADR-059's mechanism. It adds the following to the current shared schema
(finding 2). All of it is stated at schema/edge-semantic altitude — field names
and what the gate enforces — with no generator code, CLI, or scenarios.

### D1 — Carry ADR-059's typedef→generator single-source mechanism forward, unchanged

The base schema is expressed by *folding the new shared fields into the per-type
`typedef/*.yaml` single source*. The generator continues to emit both the
template (`.md`) and the JSON Schema fragment (`.json`) read-only, the `--check`
drift gate still fails CI on any hand-edit, and `x-required-sections` is
unchanged. Nothing in ADR-059's mechanism is re-opened — the additions below are
new *fields* single-sourced by the same generator, so template↔schema drift
stays impossible by construction. This is why, on acceptance, this ADR
**supersedes ADR-059**: it carries ADR-059's mechanism forward verbatim and
extends the field set it governs.

### D2 — Three materialized, gate-enforced bidirectional edge pairs

The frontmatter stores **both directions** of three relationship pairs. Each is
a list of bare artifact ids.

| Forward edge | Back-edge | Relationship |
|---|---|---|
| `supersedes` | `superseded-by` | whole-document supersession (the transformation view's spine) |
| `derives-from` | `derived-by` | the provenance spine (PDR-035 part 2): scenario→PDR→candidate→intent→session |
| `references` | `referenced-by` | a non-provenance cross-link (a decision that builds on, or is built on by, another) that is neither supersession nor derivation |

The **gate materializes and maintains** both directions and **fails on
asymmetry**: for every `A.supersedes` entry naming `B` there must be a matching
`B.superseded-by` entry naming `A`, and likewise for the other two pairs; a
dangling half-edge is a hard coherence finding, not a warning. This
**replaces the compute-transitively posture** (finding 2): because both
directions are stored, the transformation-view graph is **traversable from
frontmatter alone** — you can answer "what superseded this / what derives from
this / what references this" from a single document without scanning the corpus,
which is precisely what PDR-035's transformation view requires. The
current-system view is obtained, as PDR-035 states, by filtering to `accepted`;
self-containment is unaffected because the back-edges live in frontmatter, not
in the content sections.

`derives-from` remains a required, non-empty link (its current behavior, finding
1); its new `derived-by` back-edge is gate-maintained. `supersedes`/
`superseded-by` and `references`/`referenced-by` are optional (empty for a doc
that supersedes nothing / is referenced by nothing).

### D3 — Supersession is N:M

`superseded-by` is a **list**, and each named successor carries a matching
`supersedes` back-edge (D2). A document may therefore be **jointly superseded by
several successors** — the case PDR-035 and this restructuring rely on, where
PDR-032 is jointly superseded across slices #1/#2/#3, each successor carrying
the portion it replaces. Symmetrically, one successor may supersede several
predecessors. The gate's symmetry check (D2) holds across the full N:M set.

### D4 — A `tags` field

A `tags` field carries a free-form list of retrieval/cross-cutting labels. It is
**not** authoritative for ownership, lifecycle, or the two-views separation
(`status` alone separates the views, PDR-035); it is an aid to query and
grouping. Optional (may be empty).

### D5 — A `distribution` field: `product-lead` | `product-wide` | `bc-local` (the within-product scope axis; replaces the ADR-034/035 tier model)

A `distribution` field records the reach of the artifact, enum-constrained to
**`product-lead`** | **`product-wide`** | **`bc-local`**. This is a
**within-product SCOPE axis**, not the framework/system-global/BC-local tier
axis of ADR-034/035. The three values:

- **`product-lead`** — scoped to the lead shop's own decisions (routing, roles,
  dispatch).
- **`product-wide`** — every BC in the product must honor it.
- **`bc-local`** — one BC's internal decision; lives in the BC repo.

The scope axis **replaces the ADR-034/035 tier model wholesale** (finding 3).
The tier model's top split — `framework` vs. product tiers — forced the
"framework or product?" question, which is *unanswerable for this repo because
the product IS the framework*. The scope axis removes that question: every
artifact has an answerable within-product reach (the lead's own decisions, all
BCs, or one BC). This ADR therefore **supersedes ADR-034 and ADR-035** on
acceptance (D8), rather than reconciling with them.

`bc-local` is now a **valid** enum value (it was *excluded* under the prior
`product` | `system-wide` draft). Lead-repo instances of this schema will carry
`product-lead` or `product-wide`; `bc-local` artifacts live in BC repos (ADR-018,
ADR-035 D3) — so the field is the product's **full scope taxonomy**, not only a
taxonomy of lead-resident docs.

**Mechanism note (not a fork).** Because a lead-repo artifact is by definition
not one BC's internal decision, the coherence gate MAY assert that a lead-host
artifact instance never carries `distribution: bc-local` (a `bc-local` artifact
would be misfiled on the lead host — it belongs in a BC repo). This is a gate
mechanism detail for the downstream knowledge-BC dispatch, not an open design
question.

**Deliberately out of scope / deferred (product authority, 2026-07-26).** The
scope axis intentionally omits a `framework` value. How framework/tooling
behaviors reach a *real adopter product* without being ADRs in that product's
own corpus is a question of the **adopter boundary** and is **deferred** — it is
NOT designed here. A reader should read the absence of a `framework` value as
deliberate, pending that separate decision.

`distribution` is a **required** field on every artifact instance (it is the
schema-level successor to a property ADR-034 said every ADR "SHOULD carry"),
subject to the still-open required-vs-optional-with-default fork below.

### D6 — An external-references field

An `external-references` field carries a list of references to sources **outside
the corpus** (URLs, external documents, citations). It is distinct from the
`references`/`referenced-by` edge pair (D2), which is an **intra-corpus**
materialized edge between two artifacts and is gate-symmetry-checked; external
references point outward, are not artifact ids, and carry no back-edge. Optional
(may be empty).

### D7 — What the gate enforces (summary)

On top of ADR-059's `--check` drift gate and `x-required-sections`
body-structure check (D1), the coherence gate additionally enforces: (i) **edge
symmetry** across all three pairs (D2) — dangling half-edges fail; (ii)
**`distribution` enum validity** (`product-lead` | `product-wide` | `bc-local`) (D5); (iii)
**materialization** — back-edges are maintained, not computed on read, so the
frontmatter is the authoritative graph. The existing self-containment /
mutual-consistency posture (PDR-035) is what these checks serve; the coherence
gate that already exists is the enforcement host.

### D8 — Deferred supersession of ADR-059, ADR-034, and ADR-035 (materialize at acceptance, not while proposed)

On acceptance this ADR **supersedes ADR-059** (it carries ADR-059's mechanism
forward and folds in the base-schema fields, per the restructuring's supersession
table) **and supersedes ADR-034 and ADR-035** (the `distribution` scope field
replaces the tier model those two ADRs pin — D5, finding 3). Following the
PDR-034 precedent for a proposed successor of an accepted governing decision,
**while this ADR is `proposed`**: no `supersedes: [adr-059, adr-034, adr-035]`
frontmatter edge is declared, ADR-059/ADR-034/ADR-035 stay `accepted` and their
`superseded-by` stays empty, and `current-state.md`'s `incorporates` list is
**not** edited. The intended supersession is stated here in prose only. At the
moment of acceptance, the materialized `supersedes`/`superseded-by` edge pairs
are added (D2/D3) naming all three predecessors, ADR-059's, ADR-034's, and
ADR-035's status flips to `superseded`, and `current-state.md` gains `adr-067`
in `incorporates` per the acceptance gate. A proposed decision must not retire an
accepted governing decision — ADR-059 remains the live, incorporated format
mechanism, and ADR-034/ADR-035 remain the live tier model, until this ADR is
ratified.

**Casualty of the tier-model retirement.** ADR-035's periodic system-architect
review-cadence decision (ADR-035 D4) falls with the tier model it rode on. It
was unimplemented and unpinned (no scenario, no `bd` recurring bead ever stood
up), so nothing operational is lost; if a periodic BC-local design-coherence
review is still wanted, it can be re-raised as its own decision, decoupled from
the retired tier axis.

## Consequences

- **The transformation view becomes traversable from frontmatter alone** (D2):
  materialized back-edges replace the compute-transitively posture (finding 2),
  so "what superseded / derives from / references this" is answerable from one
  document. The current-system view (filter to `accepted`) stays self-contained
  because back-edges live in frontmatter, not content — PDR-035's requirement is
  encoded by mechanism.
- **N:M supersession is expressible** (D3), unblocking the restructuring's own
  supersession accounting (PDR-032 jointly superseded across slices #1/#2/#3).
- **Drift stays impossible by construction** (D1): the new fields are single-
  sourced by ADR-059's generator; the base schema is not a second hand-authored
  surface.
- **On acceptance, a dispatch to shopsystem-knowledge is implied — named here,
  NOT dispatched.** The knowledge BC owns the typedef/generator, the loader, and
  the coherence gate; realizing D2's edge-symmetry maintenance, D5's
  `distribution` enum, and D6's external-references field is BC work carried by a
  `request_bugfix` (tightening the existing gate/loader that already enforces
  `derives-from` and `x-required-sections`) and/or `assign_scenarios` (for the
  net-new back-edge-materialization and symmetry-failure behavior that no
  scenario pins today, finding 4). The message-type discriminator is run at
  dispatch time against the knowledge BC's then-current pre-state; it is flagged
  for the acceptance queue, not selected here.
- **The ADR-034/035 tier convention is formalized, with two open reconciliation
  points** (D5) carried to the acceptance review: the `system-global`/`system-wide`
  terminology collision, and `distribution` subsuming the informal `**Tier:**`
  tag. Neither is silently overridden.
- **Deferred materialization** (D8): while proposed, ADR-059 stays accepted and
  `current-state.md` is untouched; the supersede edges and `incorporates` update
  land at acceptance.

### Open design forks for the acceptance review (product authority)

1. **Terminology collision on `distribution: system-wide` vs ADR-035
   `system-global`** (D5). Guessed: keep PDR-035/north-star vocabulary
   (`product` | `system-wide`) and map onto the tiers. Alternative: adopt the
   ADR-035 tier names verbatim (`framework` | `system-global`) to remove the
   collision, at the cost of diverging from the north-star wording. Fork left for
   ratification.
2. **`distribution` required vs optional-with-default** (D5). Guessed: required
   on every instance (schema successor to ADR-034's "SHOULD carry"). Alternative:
   optional with a `product` default to ease migration of the legacy corpus
   (PDR-034). Fork flagged.
3. **`references`/`referenced-by` vs `derives-from` boundary** (D2). Guessed:
   `references` is the non-provenance, non-supersession cross-link; `derives-from`
   stays the provenance spine. If in practice the two blur, the acceptance review
   may collapse or sharpen the distinction.
4. **`tags` and `external-references` required vs optional** (D4/D6). Guessed:
   both optional (may be empty). Trivially reversible; flagged for completeness.
