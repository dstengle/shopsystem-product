## Context

adr-070 defines the **skill-template structure**: the common structure every
per-kind writing skill follows so the eight are consistent and generatable. But a
structure alone does not guarantee the skills exist or stay valid — pdr-038's
Options-considered explicitly rejects **advisory-only** enforcement ("kinds ship
without skills and authoring keeps improvising, leaving the authoring-guidance gap
open"). This ADR is the **enforcement** half of slice #4: shop-templates enforces,
**BLOCKING**, that (a) **every recognized kind has a writing skill** and (b) **each
skill's content is valid** — it points at the live template/schema surface rather
than embedding a frozen copy, and it covers the kind's required sections per
adr-069. Enforcement being blocking means a kind cannot ship without a valid
writing skill; that is the difference between closing the gap and papering it.

This ADR states the enforcement *rules* and their *host* at mechanism altitude —
what is checked, where, and that it blocks. It writes no gate code and no
scenarios; those are downstream shopsystem-templates / shopsystem-scenarios work
named for the acceptance queue.

### Pre-state empirical findings (artifact surface, ADR-018 D1/D2)

Verified from the lead CWD against this repo's `bin/` tooling, the installed
`shop-templates` / `shop-knowledge` / `shop-knowledge-gate` CLIs, and the
`.claude/skills/` tree. No BC source on this host (ADR-018); "empirical" is the
contract/artifact surface. This ADR **must build on the mechanisms below, not
invent a parallel one.**

1. **shop-templates is the pour/render authority for role+skill furniture.
   CONFIRMED** (`shop-templates {list,show,bootstrap,update}`; the `create-bc`
   skill records `shop-templates bootstrap … pours the canonical skill tree into
   .claude/skills/`). So shop-templates already owns *rendering* the skill tree —
   it is the natural, non-parallel host to also enforce that the rendered set
   covers every kind and that each writing skill is valid. It does **not** enforce
   any writing-skill presence/validity today (finding 4 of adr-070: no per-kind
   writing skill exists).

2. **A BLOCKING knowledge-artifact gate already exists. CONFIRMED**
   (`bin/check-knowledge-artifacts`). It runs `shop-knowledge validate` per staged
   artifact and `shop-knowledge-gate --mode distribution` corpus-wide as a
   pre-commit hook, with a deliberate **block/warn split**: a **newly-added** file
   that fails validate **BLOCKS** (exit non-zero); a modified pre-existing file
   only WARNs (Phase-5 legacy debt). The corpus coherence gate in
   **`--mode distribution` always BLOCKS**; `--mode authoring` warns and never
   blocks (`shop-knowledge-gate -h`). This is the existing blocking-enforcement
   precedent the writing-skill enforcement joins as a sibling check — not a new
   gate.

3. **bin/doctor is the aggregate per-check pass/fail precedent. CONFIRMED**
   (`bin/doctor`): each check emits a NAMED `[PASS]`/`[FAIL]` line, and doctor
   prints ONE aggregate verdict — overall pass requires EVERY check to pass, any
   single failure forces a non-zero exit naming the failed check(s). It already
   carries a `check_scenario_coherence` "every X has its Y" check. This is the
   precedent shape for "**every recognized kind** has a **valid writing skill**":
   a per-kind `[PASS]`/`[FAIL]` line, aggregate non-zero on any miss.

4. **The recognized-kind set is machine-enumerable from the single source.
   CONFIRMED** (`shop-knowledge template <kind>` / `schema <kind>` succeed for all
   eight; `schema <kind>` reports `required_sections`, `statuses`,
   `non_empty_fields`). So both the enforcement's *domain* (which kinds must have a
   skill) and its *validity target* (which required sections a skill must cover)
   are read from the same single source the writing skills reference (adr-070 D2/D3)
   — no separate list to keep in sync.

5. **`@scenario_hash` retirement enumeration. CONFIRMED — empty.** Enumerated the
   lead-held corpus (`grep -r "@scenario_hash" features/` over this repo's
   `features/` tree, the authoritative lead-side surface per ADR-018) — no Gherkin
   pins writing-skill presence/validity enforcement, so no BC-side `@scenario_hash`
   is retired, superseded, or contradicted by this landing (ADR-064 retirement
   convention: nothing to retire). The scenario/gate consequences are downstream BC
   work named for the acceptance queue, not dispatched here.

### Options considered

- **Option A — advisory-only check.** Emit a warning when a kind lacks a valid
  writing skill; do not block. **Rejected by pdr-038** and re-rejected here: an
  advisory leaves the gap open — kinds ship without skills and authoring keeps
  improvising. The whole point of this slice is to *close* the gap.
- **Option B — a new, parallel enforcement mechanism** (a bespoke writing-skill
  linter unrelated to shop-templates and the knowledge gate). Rejected: it
  duplicates the pour/render authority (finding 1) and the blocking-gate host
  (finding 2), and invites drift between two enforcement surfaces. cand-009's
  Evidence explicitly directs building on the shop-templates enforcement precedent
  (`bin/check-knowledge-artifacts`, `doctor`), not inventing a second.
- **Option C — blocking enforcement on shop-templates' existing authority, joined
  to the existing knowledge-artifact gate + doctor precedent (CHOSEN).** Two
  blocking checks (coverage + validity), hosted on shop-templates' pour/render
  authority (finding 1) and surfaced through the existing blocking gate
  (`--mode distribution`, finding 2) with a doctor-style per-kind pass/fail line
  (finding 3). No parallel mechanism; enforcement is blocking.

## Decision

**shop-templates enforces, BLOCKING, that every recognized artifact kind has a
per-kind writing skill (adr-070) and that each skill's content is valid.** The
enforcement is realized on shop-templates' existing pour/render authority (finding
1) and surfaced through the existing knowledge-artifact blocking gate (finding 2)
with a doctor-style aggregate verdict (finding 3) — **not** a parallel mechanism
(Option B). Two checks, both blocking. Stated at mechanism altitude — no gate code,
no scenarios.

### D1 — Coverage check: every recognized kind has a writing skill (BLOCKING)

For **each recognized kind** in the machine-enumerable kind set (finding 4 —
`shop-knowledge template <kind>` succeeds), there **must** exist a per-kind writing
skill (adr-070 D1: `.claude/skills/write-<kind>/`). A missing writing skill for any
recognized kind is a **hard failure** (blocking). The kind set is read from the
single source, so adding a ninth kind's typedef automatically extends the coverage
domain — no separate registry to update.

### D2 — Validity check: each skill's content is valid (BLOCKING)

Each per-kind writing skill's content **must** be valid against adr-070's
structure and adr-069's per-kind schema:

- **Points at the live template/schema, does not embed a frozen copy.** The skill
  references `shop-knowledge template <kind>` / `schema <kind>` / `validate` (adr-070
  D3 parts 2–3, D4). A skill that embeds a frozen template or schema body — the
  reuse-not-copy invariant (adr-070 D4) — is a **hard failure**.
- **Covers the kind's required sections.** The skill's lifecycle walk covers the
  kind's `required_sections`, correct starting `status`, and provenance-edge
  participation as adr-069 specifies for that kind and as `shop-knowledge schema
  <kind>` reports (finding 4). A skill that omits a required section, names a wrong
  starting status, or misstates the kind's provenance edges is a **hard failure**.

Both failure modes block; there is no warn tier for a writing skill (unlike the
legacy-corpus warn tier in finding 2, these skills are net-new — finding 4 of
adr-070 — so there is no pre-existing debt to grandfather).

### D3 — Host: shop-templates' pour/render authority, joined to the existing gate

The enforcement lives on **shop-templates**, which already owns pouring/rendering
the skill tree (finding 1) — so the check runs at pour/render time and as a
corpus-level gate, **not** as a new standalone tool (Option B). It is surfaced
through the **existing knowledge-artifact blocking gate** posture (finding 2):
blocking in the distribution/CI path, the same place `shop-knowledge-gate --mode
distribution` already hard-blocks corpus coherence. The verdict shape follows the
**bin/doctor precedent** (finding 3): one NAMED `[PASS]`/`[FAIL]` line **per
recognized kind**, an aggregate verdict that passes only if every kind passes, and
a **non-zero exit** on any miss naming the offending kind(s). The knowledge gate
enforces *artifact* coherence; this enforces *writing-skill* coverage/validity —
sibling checks on the same enforcement surface, not two competing gates.

### D4 — Advisory is rejected; enforcement is blocking (pdr-038)

Per pdr-038 (Option A rejected), the enforcement is **blocking, never advisory**. A
kind without a valid writing skill fails the gate and cannot ship. This is the
property that makes writing skills a guarantee rather than a suggestion, and it is
the enforcement counterpart to adr-070's generation discipline (which guarantees
the skills, once present, cannot drift from the typedef).

## Consequences

- **A kind cannot ship without a valid writing skill** (D1/D2/D4). The
  authoring-guidance gap pdr-038 names is closed by construction, not papered with
  an advisory that gets skipped under pressure.
- **No parallel mechanism is introduced** (D3, Option C): the enforcement rides
  shop-templates' existing pour/render authority (finding 1), the existing
  knowledge-artifact blocking gate (finding 2), and the bin/doctor per-check
  pass/fail precedent (finding 3). Two sibling blocking checks, one enforcement
  surface.
- **The coverage domain and validity target are single-sourced** (finding 4): both
  the set of kinds that must have a skill and the required sections each skill must
  cover are read from the same `shop-knowledge template`/`schema` surface the
  writing skills reference — so the enforcement cannot drift from the typedef, and
  a new kind extends the domain automatically.
- **On acceptance, dispatches are implied — named here, NOT dispatched.**
  **shopsystem-templates** owns the writing-skill enforcement and the adr-070
  skill-template-structure realization (its pour/render + role/skill discipline is
  the ubiquitous language, finding 1). **Gate rules go to shopsystem-scenarios**
  (the coverage `[PASS]`/`[FAIL]`-per-kind and validity checks as scenario-pinned
  gate behavior). The writing skills themselves **reuse the shopsystem-knowledge**
  `template`/`schema`/`validate` surface (finding 4) — no second copy. The
  message-type discriminator is run at dispatch time against each BC's then-current
  pre-state (`request_bugfix` for gate/render behavior already present;
  `assign_scenarios` for the net-new coverage/validity enforcement no scenario pins
  today, finding 5) — flagged for the acceptance queue, not selected here.
- **No supersession edge while proposed.** New capability — this ADR supersedes
  nothing; its `derives-from` runs to `adr-070` (the skill-template structure this
  enforcement builds on) and `pdr-038` (the needs), both of which exist, so the
  provenance gate is satisfied.

### Open design forks for the acceptance review (product authority)

1. **Enforcement trigger point — pour/render time vs commit gate vs both** (D3).
   Guessed: both — validate at shop-templates pour/render AND as the
   distribution-mode blocking gate (matching the existing knowledge-artifact gate's
   pre-commit + CI posture, finding 2). The authority may narrow to one; flagged.
2. **Validity-check depth** (D2). Guessed: structural — the skill references the
   live template/schema surface (reuse-not-copy) and covers the kind's required
   sections / starting status / provenance edges per adr-069. Whether to also
   assert deeper prose-quality properties of the lifecycle walk is a
   heavier check left out here; flagged as a follow-on if structural proves
   insufficient.
3. **Consult-decision-index coupling** (inherited from adr-070 fork 2, lead-x7bp
   lineage). If the authority later bakes accepted-decision-context injection into
   the writing skill, this enforcement would extend to check that coupling too.
   Recommendation carried from adr-070: keep OUT for now; flagged as a follow-on.
