## Context

PDR-032 owns the artifact type system as one **bundled taxonomy** — the eight
kinds, their per-type id patterns, status enums, link fields, and gate rules are
all legible to the generator but stated as one lump, not as a per-kind contract.
ADR-067 (slice #2, proposed) established the **base schema**: the shared
frontmatter every kind carries (`type, id, title, status, created, updated,
authors, description`), the three materialized bidirectional edge pairs
(`supersedes`/`superseded-by`, `derives-from`/`derived-by`,
`references`/`referenced-by`), N:M supersession, and the `tags`, `distribution`,
and `external-references` fields. pdr-037 (slice #3, proposed) states the per-type
**needs** — why each kind exists and what it is for. This ADR is the paired
per-type **schema**: for each of the eight kinds, *what it adds to or constrains
beyond the base schema*. It states nothing at generator/CLI altitude; it is the
schema spec the shopsystem-knowledge per-type typedefs realize.

This is **additive on ADR-067 and supersedes nothing**. ADR-067 already carries
the supersession of ADR-059; this ADR only refines, per kind, the shared contract
ADR-067 defines. On acceptance, this ADR — with slices #1 and #2 — jointly
supersedes PDR-032 (the N:M supersession ADR-067 D3 makes expressible), re-homing
PDR-032's per-type-taxonomy content into the eight sections below.

### Pre-state empirical findings (artifact surface, ADR-018 D1/D2)

Verified from the lead CWD against this repo's `adrs/`/`pdrs/` records and the
installed knowledge tooling (`shop-knowledge schema <kind>`,
`shop-knowledge template <kind>`, `shop-knowledge-gate`). No BC source on this
host (ADR-018); "empirical" is the contract/artifact surface.

1. **The eight per-type typedefs are the current single source and each already
   carries per-type required sections, a status enum, and per-type link fields.
   CONFIRMED** (`shop-knowledge schema <kind>` / `template <kind>` for all eight).
   The `shared_required_fields` set is identical across all eight and equals
   ADR-067's base set (`type, id, title, status, created, updated, authors,
   description`), so the per-type deltas below are exactly the additive surface
   this ADR governs — it never re-declares those eight fields.

2. **`derives-from` requiredness is per-type, not base. CONFIRMED.** `derives-from`
   is *not* in any kind's `shared_required_fields`; it appears in
   `type_required_fields` for adr, pdr, brief only, and is `non_empty` only for
   adr. intent-record, candidate, session-record, current-state, and
   prioritization-record do not require it. So "which kinds require a non-empty
   provenance edge" is a per-type constraint stated below, reconciling ADR-067
   D2's prose ("`derives-from` remains a required, non-empty link") down to the
   kinds that actually carry that constraint.

3. **The current-state typedef is internally inconsistent, and the live instance
   diverges from both. CONFIRMED.** `shop-knowledge schema current-state` reports
   `id_pattern: current-state-\d{3,}` (versioned NNN) and `statuses:
   [current, superseded]` (supersede-able) — a versioned model — yet
   `document_shape: living` and the generated template comment say "LIVING
   DOCUMENT — a single record stewarded in place … rather than appending a
   numbered-series instance." The live `current-state.md` carries `id:
   current-state` and `status: live` — neither the versioned id pattern nor a
   value in the typedef's status enum. Three surfaces disagree; this ADR resolves
   the model (D7 below) and scopes the instance migration as a follow-on.

4. **`@scenario_hash` retirement enumeration. CONFIRMED — empty.** This is a
   schema/typedef decision. Enumerated the lead-held corpus
   (`grep -r "@scenario_hash" features/` over this repo's `features/` tree, the
   authoritative lead-side surface per ADR-018) — no Gherkin pins the
   artifact-frontmatter per-type schema, so no BC-side `@scenario_hash` is retired,
   superseded, or contradicted by this landing. The scenario-register consequences
   are downstream BC work named for the acceptance queue, not dispatched here.

### Options considered

- **Option A — leave the per-type contracts bundled in PDR-032.** Rejected: no
  per-kind authoritative schema, and PDR-032 cannot be cleanly superseded (a
  founding doc stays accepted carrying content the new family also claims). This
  is the status quo pdr-037/intent-010 exist to end.
- **Option B — eight separate per-type schema ADRs.** Rejected for now: eight
  near-parallel additive deltas are heavier to author/review while proposed and
  are better seen together against one base. Re-split remains the authority's call
  at acceptance (design fork below), mirroring pdr-037's granularity flag.
- **Option C — one sectioned per-type schema ADR, additive on ADR-067 (CHOSEN).**
  One section per kind, each stating only its delta over the base. Pairs 1:1 with
  pdr-037's per-type needs sections; keeps the additive discipline visible against
  a single base.

## Decision

For each of the eight kinds, the schema states **only** what that kind adds to or
constrains beyond ADR-067's base schema: its **required body sections**, its
**`status` enum**, and its **edge participation** (which base edges it uses, which
it requires non-empty, and any per-kind link field). The base frontmatter
(`type, id, title, status, created, updated, authors, description`), the three
edge pairs, N:M supersession, and `tags`/`distribution`/`external-references` are
inherited from ADR-067 and are **never re-declared** here. All eight remain
single-sourced from their per-type typedef by ADR-059's generator (carried forward
by ADR-067 D1); this ADR is the schema spec those typedefs realize, at schema
altitude only — no generator code, no CLI, no scenarios.

Cross-cutting, inherited from the base and NOT re-stated per kind: every kind
carries the base frontmatter; every kind may participate in
`references`/`referenced-by` and may carry `tags`, `distribution` (required,
`product` | `system-wide`, ADR-067 D5), and `external-references`. The
per-kind sections state only the deltas.

### D1 — adr (decision record)

- **id pattern:** `adr-NNN`. **document shape:** instance.
- **status enum:** `proposed` | `accepted` | `superseded` | `rejected`.
- **required sections (add):** `Context`, `Decision`, `Consequences`.
- **edge participation (constrain):** requires **`derives-from` non-empty** (the
  only kind for which the provenance edge is non-empty-required, finding 2);
  participates in `supersedes`/`superseded-by` (an ADR supersedes prior ADRs,
  N:M per ADR-067 D3). An accepted ADR must be claimed by some `current-state`
  `incorporates` edge (see D7).
- **note:** ADR instances conventionally carry `decision-makers` (this ADR does),
  but the adr typedef does **not** schema-require it today (finding 1); pdr does.
  Whether to schema-require `decision-makers` on adr is a design fork below, not
  decided here.

### D2 — pdr (product decision record)

- **id pattern:** `pdr-NNN`. **document shape:** instance.
- **status enum:** `proposed` | `accepted` | `superseded` | `rejected`.
- **required sections (add):** `Context`, `Options considered`, `Decision`,
  `Consequences`.
- **edge participation (constrain):** requires `decision-makers` and
  `derives-from` (required, empty permitted — not `non_empty`, unlike adr,
  finding 2); `derives-from` runs to the originating `candidate`. Participates in
  `supersedes`/`superseded-by`, N:M — this is the edge that carries the joint
  supersession of PDR-032 across slices #1/#2/#3 (ADR-067 D3).

### D3 — brief

- **id pattern:** `brief-NNN`. **document shape:** instance.
- **status enum:** `draft` | `ready` | `delivered` | `withdrawn` (a delivery
  lifecycle, distinct from the proposed/accepted decision lifecycle).
- **required sections (add):** `Summary`, `Scope`.
- **edge participation (constrain):** requires `derives-from` (its `candidate`);
  participates in `references`. PDR-032's rule "`brief.candidate` required for
  briefs beyond 015" re-homes here as the `derives-from`→candidate requirement,
  with the "beyond 015" threshold read as a legacy-corpus grandfather clause
  (legacy migration is out of appetite per PDR-032 and this slice).

### D4 — intent-record

- **id pattern:** `intent-NNN`. **document shape:** instance.
- **status enum:** `recorded` (single terminal state — an intent is captured, not
  lifecycled).
- **required sections (add):** `Verbatim anchors`, `The goal behind the ask`,
  `Who it serves`, `Constraints`, `Non-goals`, `Appetite signal`,
  `Failure conditions`, `Open threads`.
- **edge participation:** the **head of the provenance spine** — it does *not*
  require `derives-from` (finding 2); it is the target a `candidate`'s
  `derives-from` runs to, and it is produced by a `session-record` (its `produced`
  list, D6). Carries optional per-kind fields seen in instances (`stakeholder`,
  `session`); `superseded-by` is the inherited base back-edge (D-of-ADR-067), not
  re-declared here.

### D5 — candidate

- **id pattern:** `cand-NNN`. **document shape:** instance.
- **status enum:** `exploring` | `shaped` | `briefed` | `committed` | `parked` |
  `rejected`.
- **required sections (add):** `Verbatim anchors`, `Problem`, `Appetite`,
  `Solution sketch`, `Rabbit holes`, `No-gos`, `Evidence / experiments`,
  `Resolution`, `Changelog`.
- **edge participation:** `derives-from` runs to its `intent-record` (carried in
  instances; not schema-required non-empty, finding 2). **Status-coupled gate rule
  (re-homed from PDR-032):** `status: briefed` ⇒ a brief exists for it and the
  brief backlinks the candidate. Carries optional per-kind fields
  (`session`, `experiments`, `brief`, `parked-until`).

### D6 — session-record

- **id pattern:** `sess-YYYY-MM-DD-x`. **document shape:** instance.
- **status enum:** `open` | `closed`.
- **required sections (add):** `Outcome`, `Open threads`.
- **edge participation (constrain):** requires the per-kind link fields
  `produced` and `revised` (the two lists that make a session the **root
  producer** of the provenance spine: it produces intents/candidates). **Gate rule
  (re-homed from PDR-032):** `status: closed` ⇒ at least one entry across
  `produced`/`revised`.

### D7 — current-state (RESOLVED: versioned)

- **id pattern:** `current-state-NNN`. **document shape:** **instance
  (versioned, supersede-able)** — this ADR flips `document_shape` from the
  typedef's current `living` to align it with the versioned id pattern and status
  enum the same typedef already carries (finding 3).
- **status enum:** `current` | `superseded`.
- **required sections (add):** `Current decisions`, `Stewardship`.
- **edge participation (constrain):** requires `incorporates` (the list of
  accepted PDR/ADR ids the snapshot reflects); participates in
  `supersedes`/`superseded-by` — **each new snapshot is accepted as `current` and
  supersedes the prior snapshot (which flips to `superseded`)**. **Gate rule
  (re-homed from PDR-032):** every accepted PDR/ADR must be claimed by some
  `current-state` `incorporates` edge.

**Resolution and rationale.** current-state is **VERSIONED**, not a singleton
rewritten in place. The versioned model is the only one that is internally
consistent with the typedef's own `current-state-NNN` id pattern and
`current`/`superseded` status enum, and it is the one cand-008/intent-010 lean to.
Decisively, it *fits PDR-035's two-views framing*: each accepted snapshot is a
`current`-status **current-system view**, and the chain of `superseded` priors is
exactly the **transformation view** of how the product's state evolved — the same
supersede-spine every other kind rides, now available for the state fact sheet
too. The singleton-rewritten-in-place model discards that history and keeps the
standing typedef-vs-instance disagreement alive. Choosing versioned removes the
three-way divergence (finding 3) by conforming the model to the versioned side
and scheduling the instance to follow.

**Instance migration is a scoped follow-on — NOT done here.** Materializing this
decision means the live singleton `current-state.md` (`id: current-state`,
`status: live`) becomes `current-state-001` (`status: current`), and each
subsequent state edit becomes a new accepted `current-state-NNN` superseding its
predecessor. That migration touches a live instance and is out of this slice's
schema decision; this ADR **does not edit `current-state.md`** and does not
perform the migration. It is flagged for the acceptance queue as a genuine
product decision (design fork below).

### D8 — prioritization-record

- **id pattern:** `prio-NNN`. **document shape:** instance.
- **status enum:** `draft` | `active` | `superseded`.
- **required sections (add):** `Ranking`, `Rationale`.
- **edge participation:** participates in `supersedes`/`superseded-by` — a newer
  `active` record supersedes the prior (matching the lead-shop rule that dispatch
  order answers to the *latest ratified* record and a superseded record no longer
  moves the queue); `references` the candidates/beads it ranks. `derives-from` is
  optional.

### D9 — Additive discipline and PDR-032 coverage

Each section above states a **delta only**; a per-type schema that re-declares a
base field is a defect (it would drift from ADR-067). The union of the eight
sections re-homes PDR-032's **per-type taxonomy** content — the eight kinds, their
per-type id patterns, status enums, required sections, link fields, and the
status-coupled gate rules (candidate→briefed, closed-session→produced/revised,
accepted-decision→incorporates, brief→candidate). PDR-032's **base-field** content
(`type`, `description`, `created`/`updated`/`authors`) and its **cross-cutting
gate** content (link resolution across the eight types; draft-age advisories)
re-home to slice #2 (ADR-067); its **founding/ownership** content (ownership,
`type` unification, cost, pour fencing, boundary rules) re-homes to slice #1. The
coverage check (below) confirms nothing is orphaned when PDR-032 is jointly
superseded.

## Consequences

- **Each kind's schema stands on its own, additive on one base.** The type system
  is legible per kind rather than as one bundled taxonomy, and the additive
  discipline (D9) keeps every per-type schema single-sourced against ADR-067 with
  no base-field duplication to drift.
- **PDR-032's per-type taxonomy re-homes cleanly** into the eight sections. With
  slices #1 (founding) and #2 (base fields + cross-cutting gate), the joint
  supersession of PDR-032 is coverage-complete — nothing orphaned (coverage check
  below). The N:M supersession that carries it is ADR-067 D3's, materialized at
  acceptance, not declared here.
- **The current-state model is decided: versioned** (D7). This ends the three-way
  divergence between the typedef's versioned id/status, its `living` shape, and
  the live singleton instance. The **instance migration** (singleton →
  `current-state-001`) is a **scoped follow-on**, explicitly not performed here;
  `current-state.md` is untouched by this ADR.
- **On acceptance, a dispatch to shopsystem-knowledge is implied — named here,
  NOT dispatched.** The knowledge BC owns the per-type typedefs, the generator,
  and the coherence gate. Realizing this ADR means: refine the eight per-type
  typedefs so the generated schema/template match the per-type deltas above
  (notably flipping current-state's `document_shape` to versioned/instance and
  reconciling its status enum against the live instance), and land the
  status-coupled gate rules (D5/D6/D7) as the per-type checks. The message-type
  discriminator is run at dispatch time against the knowledge BC's then-current
  pre-state (a `request_bugfix` tightening for typedef fields already generated;
  `assign_scenarios` for any net-new gate behavior no scenario pins today,
  finding 4); it is flagged for the acceptance queue, not selected here.
- **No supersession edge is declared while proposed.** This ADR supersedes
  nothing (it is additive on ADR-067, which already supersedes ADR-059); its
  `derives-from` runs to `adr-067` and `pdr-037`, both of which exist, so the
  provenance gate is satisfied. `current-state.md`'s `incorporates` is untouched
  until this ADR is accepted (ADR-067 D8 deferred-supersession posture).

### PDR-032 coverage check (result)

Every PDR-032 **per-type taxonomy** claim lands in a per-type section above:

| PDR-032 claim | lands in |
|---|---|
| the eight kinds enumerated | D1–D8 (all eight) |
| per-type id patterns | each section's *id pattern* |
| per-type status enums | each section's *status enum* |
| per-type required sections | each section's *required sections* |
| per-type link fields | each section's *edge participation* |
| candidate==briefed ⇒ brief-set + backlink (rule 5b) | D5 |
| brief.candidate required (rule 5c) | D3 |
| closed-session ⇒ ≥1 produced/revised (rule 5d) | D6 |
| accepted PDR/ADR claimed by `incorporates` (rule 5e) | D7 (+ D1/D2 note) |

Claims that re-home **out of this slice** (correctly, not orphaned): base-field
content (`type`, `description`, `created`/`updated`/`authors`, item 3/4) → slice #2
(ADR-067); cross-cutting gate rules — link resolution across the eight types
(rule 5a) and draft-age advisories (rule 5f) → slice #2's base gate (ADR-067 D7);
ownership, `type` unification, cost, pour fencing, boundary rules (items 1/2/6/7/8)
→ slice #1 founding. **Result: nothing orphaned** — the joint supersession of
PDR-032 across slices #1/#2/#3 is coverage-complete.

### Open design forks for the acceptance review (product authority)

1. **current-state versioned vs singleton** (D7). Decided here: **versioned**
   (internally consistent with the typedef's id/status; fits PDR-035's two-views
   framing). Alternative: keep the singleton-rewritten-in-place living doc and
   instead conform the typedef's id pattern/status *down* to a singleton. This is
   a genuine product decision — flagged for ratification, and it gates the scoped
   instance-migration follow-on (`current-state` → `current-state-001`).
2. **One sectioned schema ADR vs eight per-type ADRs** (Option B). Guessed: one
   sectioned doc while proposed, mirroring pdr-037's granularity flag. The
   authority may re-split at acceptance.
3. **Schema-require `decision-makers` on adr** (D1). Today the adr typedef does
   not require it though instances carry it; pdr does require it. Guessed: leave
   as-is (convention, not schema). Alternative: tighten the adr typedef to require
   it, harmonizing with pdr. Flagged.
4. **current-state status enum vs the live instance** (D7/finding 3). The live doc
   uses `status: live`, which is not in the typedef enum `{current, superseded}`.
   Guessed: the migration adopts `current` for the head snapshot. Whether to also
   admit a `live` alias is a migration-time question, flagged with the instance
   migration.
