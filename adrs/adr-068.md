## Context

PDR-036 (slice #1 of this fold, proposed) commits the corpus to **one read-only
CLI** over the artifact frontmatter graph with three verbs — navigate, render
with view filtering, query by frontmatter — at capability altitude, and
deliberately hands the field/flag/edge mechanics to a mechanism ADR gated behind
the base-schema ADR. PDR-035 (slice #1 of the parent restructuring, proposed)
states the **two-views/self-containment requirement**: the `accepted` set read
together is the *current-system view* (self-contained, changelog filtered out),
and the full graph including superseded docs and the supersede chains is the
*transformation view*, with `status` as the separating axis. ADR-067 (slice #2,
proposed) is the **base schema** that materializes the graph this CLI reads:
three gate-maintained bidirectional edge pairs (`supersedes`/`superseded-by`,
`derives-from`/`derived-by`, `references`/`referenced-by`), N:M supersession, and
the `tags` / `distribution` / `external-references` fields.

This ADR is the **read-side mechanism**: what the CLI surface is, what each verb
does over the frontmatter graph, and which existing knowledge-BC machinery it
reuses. It writes no generator code, no BC implementation, and no scenarios —
those are downstream BC work named for the acceptance queue. It states the CLI
at schema/mechanism altitude (the verb set, the view-filter semantics, the loader
reuse contract, the read-only invariant), not at implementation altitude.

### Pre-state empirical findings (artifact surface, ADR-018 D1/D2)

Verified from the lead CWD against this repo's `adr/`/`pdr/` records and the
installed knowledge tooling (the `shop-knowledge` / `shop-knowledge-gate` CLIs
and the `knowledge` package they run). No BC source is read or executed on this
host (ADR-018 D1); the package inspected here is the *installed contract tool*,
whose surface is a contract fact.

1. **The corpus read tooling does not exist today. CONFIRMED** (ran
   `shop-knowledge` with no subcommand → `a subcommand is required (template,
   schema, validate)`). The installed CLI exposes only `template`, `schema`, and
   `validate`; there is **no** navigate, render, or query verb, and no
   view-filtering surface. This slice is therefore **net-new capability** on the
   read side, not a tightening of an existing verb — the message-type
   discriminator at acceptance resolves against the knowledge BC's then-current
   pre-state (Consequences), and the net-new verbs read as `assign_scenarios`
   while any tightening of the shared loader reads as `request_bugfix`.

2. **The corpus loader already exists and is already reused by the gate.
   CONFIRMED** (read of `knowledge/corpus_loader.py`; grep of usages). The loader
   is `knowledge.corpus_loader.load_corpus(root) -> ArtifactCorpus`: it is the
   *filesystem boundary* that walks the per-type subdirectories plus the living
   `current-state.md`, parses each document's YAML frontmatter, and hands the
   result to `ArtifactCorpus`. The coherence gate already consumes it —
   `knowledge.coherence_cli.load_and_run` calls `load_corpus(root)` and runs the
   lifecycle checks over the result. This is the single loader the three verbs
   reuse; there is no second graph reader to fork.

3. **The corpus abstraction and the edge-resolution surface the verbs need
   already exist as library surface. CONFIRMED** (read of
   `knowledge/coherence.py`, `knowledge/typed_edges.py`). `ArtifactCorpus`
   exposes `by_id` (the full id index), `get(id)`, and `of_type(type_name)`.
   Edge resolution is `knowledge.typed_edges.resolve_edges(corpus) ->
   tuple[Edge, ...]`, where each `Edge(source, link_field, target, resolved)` is
   read purely from a frontmatter link field in `LINK_FIELDS` (never from body
   prose). `resolve_edges` is **field-driven**: it materializes an edge for every
   `LINK_FIELDS` value present, so it traverses whatever fields the schema
   populates — which is exactly the seam ADR-067 extends when it adds the three
   materialized bidirectional pairs to the shared schema. The CLI's `navigate`
   verb consumes this resolved edge set; it does not re-derive the graph.

4. **A body-projection surface exists but carries no two-views filter yet.
   CONFIRMED** (read of `knowledge/projections.py`). The module already parses
   frontmatter, extracts the decision section, and emits `L0`/`L1`/
   `ProjectionBundle` projections — but there is **no** current-system vs
   transformation view filter that drops the changelog and superseded/
   transformation material. So `render`'s section-parsing substrate is reusable,
   while the **view filter itself is net-new** and is the single most
   correctness-sensitive part of this slice (the cand-007 rabbit hole: the filter
   must *drop* changelog and transformation material, not merely hide `status`).

5. **`@scenario_hash` retirement enumeration. CONFIRMED — empty.** This is a
   read-side CLI mechanism decision; no lead-held Gherkin in `features/` pins the
   corpus read tooling, so nothing is retired, superseded, or contradicted by
   this landing. The scenario-register consequences are downstream BC work named
   for the acceptance queue (Consequences), not dispatched here.

### Options considered

- **Option A — No dedicated read tooling; rely on the gate plus manual
  frontmatter reading (status quo, finding 1).** Rejected for the same reason
  PDR-036 rejects it: the two views stay theoretical and self-containment cannot
  be relied on when obtaining the current view is a manual, error-prone step.
- **Option B — A second, purpose-built graph reader for the read verbs.**
  Rejected: findings 2–3 show the loader (`load_corpus`), the corpus abstraction
  (`ArtifactCorpus`), and the edge-resolution pass (`resolve_edges`) already
  exist and are already the gate's substrate. A second reader forks the graph and
  drifts from the gate's view of the same corpus — the cand-007 rabbit hole made
  explicit.
- **Option C — One read-only CLI, three verbs, over the *existing* shared loader
  and edge-resolution surface (CHOSEN).** A single command surface reuses
  `load_corpus`/`ArtifactCorpus`/`resolve_edges` once per invocation and layers
  navigation, view-filtered rendering, and frontmatter query on top. One loader,
  one view-filter implementation, one surface kept coherent with ADR-067's
  schema.

## Decision

The corpus gains **one read-only CLI surface** over the artifact frontmatter
graph, with three verbs, expressed at schema/mechanism altitude. It is realized
by the shopsystem-knowledge BC (which owns the loader, the gate, and the CLI). No
implementation code, generator code, or scenarios are written here.

### D1 — One read-only CLI, three verbs, over the shared loader

A single read-only command surface carries three verbs — `navigate`, `render`,
`query`. Every invocation loads the corpus **once** through the knowledge BC's
existing `load_corpus(root) -> ArtifactCorpus` (finding 2) and reads from that
one in-memory corpus; the three verbs are three read paths over a single shared
loader, not three tools. The CLI adds **no second graph reader** and **no second
frontmatter parser**: navigation consumes `resolve_edges(corpus)` (finding 3),
and rendering reuses the `knowledge.projections` section-parsing substrate
(finding 4). This directly discharges PDR-036's "one CLI over one loader" and
cand-007's "do not re-implement the loader" rabbit hole.

### D2 — The read-only invariant, and the boundary with ADR-067's gate

Every verb is **strictly read-only**: it never writes, mutates, or maintains an
artifact or an edge. Edge *materialization and symmetry maintenance* is
ADR-067's gate's job (ADR-067 D2/D7); this CLI only *traverses* the edges the
gate has already materialized. The read/write split is a hard boundary of this
decision — the read CLI and the coherence gate are two consumers of the same
loader, one read-only and one maintaining, and this ADR owns only the read-only
one.

### D3 — `navigate`: the edge-neighbourhood from a document id

`navigate` takes an artifact id and returns that document's **edge-neighbourhood**
— the set of edges incident on it, each as `(link_field, target, resolved)` plus
the neighbour's id/type/status/title — computed from `resolve_edges(corpus)`
(finding 3) over the frontmatter graph. Because ADR-067 materializes both
directions of the three edge pairs, the neighbourhood is answerable from the
single named document's frontmatter without a corpus scan (ADR-067 D2): forward
and back edges (`supersedes`/`superseded-by`, `derives-from`/`derived-by`,
`references`/`referenced-by`) are both traversable. A **direction filter**
(forward edges only, back edges only, or both) selects which half of the pairs
the neighbourhood returns. `navigate` reports `resolved: false` / legacy-target
status faithfully rather than hiding an unresolved edge — it surfaces the graph
the gate maintains, it does not sanitize it.

### D4 — `render`: view filtering on the `status` axis

`render` takes an artifact id and a **view selector** and emits that one
document, filtered:

- **current-system view** — the document's `accepted` content sections only. The
  **changelog is dropped** (PDR-035 part 4: the changelog is the one sanctioned
  transformation-view exception and is filtered out of the current-view render),
  and any superseded/transformation material is dropped. A document whose
  `status` is not `accepted` has no current-system rendering — the current view
  is, by construction, the `accepted` set (PDR-035 part 3).
- **transformation view** — the full document, including the changelog and any
  supersede-chain material.

The selector is the **`status` axis** (PDR-035): current-system = filter to
`accepted` and drop the changelog/transformation material; transformation = full.
The view filter is a section-level drop layered on the existing
`knowledge.projections` section-parsing substrate (finding 4); it is **not** a
second markdown parser and **not** a mere `status`-hide. The correctness property
this verb must hold — the cand-007 named rabbit hole — is that the current-system
render **drops** changelog and transformation material rather than merely hiding
`status`; leaking transformation material into the current view defeats the
self-containment requirement the whole slice exists to serve.

### D5 — `query`: selection by frontmatter and edge participation

`query` selects documents from the loaded corpus by frontmatter facets — **type,
status, tag, distribution** (the `tags` and `distribution` fields ADR-067 adds)
— and by **edge participation** (documents that carry, or are the target of, a
named edge; e.g. "everything `superseded-by` something", "everything that
`references` adr-067"). Selection is confined to **frontmatter fields and edges**
only — cand-007's no-go: **no general query expression language** grows beyond
frontmatter/edge selection. `query` returns either:

- a **compact list** — one line/record per match carrying id/title/status (the
  `projections.L0`-shaped card), or
- the **matching documents rendered**, reusing D4's view filter unchanged so the
  same current-system/transformation semantics apply to a query result set.

### D6 — Output formats and the shared serialization

All three verbs support **md / json / yaml** output. `navigate`'s neighbourhood
and `query`'s compact list are structured records (json/yaml natural, md as a
readable table/list); `render` and query-with-rendering emit document markdown,
or a json/yaml envelope wrapping the rendered body plus the frontmatter facets.
Output selection is a single shared flag across the three verbs — one serializer,
not three.

### D7 — Sequencing: this mechanism rests on ADR-067's materialized edges

`navigate` and edge-participation `query` (D3/D5) are only meaningful once the
three bidirectional edge pairs are **materialized** in frontmatter — the
compute-transitively posture ADR-067 replaces (ADR-067 finding 2 / D2). The
edge-resolution surface (`resolve_edges` / `LINK_FIELDS`, finding 3) is
field-driven, so this CLI traverses whatever the schema populates; it is ADR-067
that populates the three pairs into that schema. This ADR therefore **derives
from ADR-067** and is authored after it, per PDR-036's sequencing. If ADR-067's
open fork on the `references`/`derives-from` boundary (ADR-067 fork 3) shifts,
the edge set `navigate`/`query` traverse shifts with it — no change to this
mechanism, only to the fields it reads.

## Consequences

- **The two-views requirement becomes mechanically obtainable** (PDR-035, PDR-036):
  a reader produces the current-system view by `render --view current-system`
  (changelog + transformation material dropped) rather than by hand-reading
  `status` and manually filtering — the error-prone practice the requirement
  exists to eliminate. The transformation graph is walkable via `navigate` over
  ADR-067's materialized back-edges.
- **The read side stays coherent with the schema and with the gate** (D1/D2):
  one loader, one corpus abstraction, one edge-resolution pass, shared between
  the read CLI and the coherence gate. No drift-prone second graph reader
  (cand-007 rabbit hole closed by construction).
- **On acceptance, a dispatch to shopsystem-knowledge is implied — named here,
  NOT dispatched.** The knowledge BC owns the loader, the gate, and the CLI.
  Realizing the three read verbs is net-new read-side behavior no scenario pins
  today (finding 1), so the net-new verbs read as `assign_scenarios`; any part
  that only *tightens* the already-shared loader/projection surface reads as
  `request_bugfix`. The message-type discriminator is run at dispatch time
  against the knowledge BC's then-current pre-state; it is flagged for the
  acceptance queue, not selected here.
- **This mechanism is gated behind ADR-067** (D7): the read verbs over edges are
  meaningful only once the bidirectional pairs are materialized. Accepting this
  ADR before ADR-067 lands would ship a `navigate`/edge-`query` surface with no
  back-edges to traverse; the acceptance order is ADR-067 then ADR-068.

### Open design forks for the acceptance review (product authority)

1. **`navigate` neighbourhood depth: 1-hop vs transitive walk** (D3). Guessed:
   `navigate` returns the **immediate (1-hop) edge-neighbourhood** with a
   direction filter; a transitive/closure walk (e.g. the full supersede chain or
   the full provenance spine in one call) is deferred so the verb stays a bounded
   graph read rather than a traversal language. Alternative: a `--depth` flag for
   bounded multi-hop. Fork left for ratification.
2. **`query` default result shape: compact list vs rendered documents** (D5).
   Guessed: the **compact list is the default**, with an opt-in flag to render
   matches (so a broad query does not render the whole corpus by accident).
   Alternative: default to rendered current-system view. Trivially reversible;
   flagged.
3. **What counts as "transformation material" beyond the changelog in the
   current-system render** (D4). Guessed: the current-system render drops the
   **changelog section** (PDR-035's one sanctioned exception) and never emits
   non-`accepted` documents; no other in-body section is treated as
   transformation material, because PDR-035 binds self-containment to content
   sections and names only the changelog as the exception. If a future doc shape
   carries an explicit transformation-only section, the acceptance review may
   name it here. Fork flagged.
4. **`navigate`/`query` treatment of unresolved and legacy-target edges** (D3).
   Guessed: surfaced faithfully with their `resolved: false` / unverifiable-legacy
   status (D3) rather than filtered out, so the read CLI reflects the graph the
   gate maintains. Alternative: a `--resolved-only` filter for a clean view. Fork
   flagged for completeness.
