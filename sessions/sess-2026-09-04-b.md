## Outcome

**Mode: discovery (brainstorm)** on work item lead-1kp6m, from the
authority's direction of 2026-09-04 filed as lead-spnnl. Converged:
"Keep the hinge, one session, converge." Recorded as
[init-request-routing](../initiatives/init-request-routing.md),
`proposed`, owner lead-pm.

### Authority's words (select quotes)

- Intake: "All requests are for the product unless they are pointed at
  the configuration of the shopsystem itself. And this shop is the lead
  for the shopsystem itself, which is somewhat recursive, but requests
  to change the behavior of the underlying system just mean modifying
  the product and then upgrading the shop." — "intake needs to be able
  to do routing regardless of 2)".
- Small-change lane: "There needs to be a small-change lane that even
  includes features, however minor. For instance I want to
  decision-brief to have metadata pointing to whatever it is related
  to. This is a trivial, but functional change that shouldn't require
  a lot of process."
- Configuration: "instance-local role and process decisions by the
  user 'Add xxx to the lead-pm role locally' or operational changes
  like the runtime back-end of the bc shops, connection management for
  LLMs, etc." — "this goes to backlog - we are not working through any
  new types".
- Routing: "Lead-pm should handle routing and all requests should be
  recorded and rejection handled with the product authority, since the
  lead-pm is an extension of the human authority."
- Request as front end: "I want request to become the front-end record
  for anything done by the system, since we don't have a good
  entry-point to go from open-ended human input to something an agent
  can work with. The router can use open-discussion with the user to
  evaluate whether a request is being made and then route that
  request. It does not need to be fully formed … This gives us a
  transition from transcript -> conversation that has been missing. It
  also gives us a way to deal with possibly extraneous requests that
  pop up in other processes, like backlog requests, etc."
- On the small artifact: "a request specialization might be a separate
  artifact with a different name like 'small-feature-task' or
  'feature-task' with size 'small', however we handle it." The lead-pm
  recommended a feature with a size, framed by its request, no new
  type; the authority did not object and converged on the draft that
  carried it.
- Originator's words: "should be linked, but referenced. The framing
  should go through refinement with the human".
- Work register: "the problem is that we have no process for handling
  the pileup. These should all be in the backlog and grooming should
  prioritize all open work, not just big initiatives." — "beads is not
  intended to be a system of record beyond current work in motion.
  Losing beads should not result in losing context about the system
  other than what is currently being executed."
- Scope: "Grooming change and drain are out of scope, this is about
  getting simple things done, which now requires being able to route
  requests."

### Positions reached

- The request is the front-end record for every ask and the durable
  one; the work register holds work in motion only and points at it.
- The lead-pm routes and records; rejection is handled with the
  authority. Destinations: discovery, the small lane, decline.
- The small lane is a feature with a size, framed by its request; no
  new artifact type.
- The hinge stays in scope: discovery accepts a request as its input
  and the initiative can reference it.
- Appetite: one working session of the lead shop.
