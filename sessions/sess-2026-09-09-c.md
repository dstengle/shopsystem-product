## Outcome

**Mode: discovery**, form brainstorm, on the parked request
req-2026-09-09-lead-shop-builds, opened by the product authority.
Anchor: lead-z2nit. Converged; the authority said "bet".

### What the conversation moved

It opened on the recorded gap (lead-ki66p): nothing defines the step
where the lead shop builds an assignment it holds itself, so every
internal build ran on a bead no process opened and its cost landed on
no initiative. Six candidate shapes were put; the authority took none
of them and reframed twice.

**First reframing (exchange 2).** "What would make sense is if the
lead has the same implementation as any other BC and then it could
execute the same process for the things it owns within its own code
repository" — the code boundary kept, no Bounded Context drawn around
the corpus, nothing deployed back in. With it, a second move: "There
needs to be some kind of designation for what a bounded context is
responsible for, who else depends on it and how that dependency is
met." That second move was split to the operational-contract
discovery (lead-bmmzh).

**Two corrections (exchange 3).** "An install (or rendering) is not a
second home. Templates were always re-installed from the canonical
definition... The versioning can be kept in the files, generated at
build time for the package." And: "I do not want to pull development
process from main. We need to define the roles and process using our
new system... the prompts for the implementation roles were lacking
and are part of the reason why we have rebaseline in the first place."
The lead-pm's recommendation to import the build process from `main`
was withdrawn.

**The centre named (exchange 4).** "The missing definition of good had
a big impact on code-quality over time and is one of the prime
motivators for the rebaseline: defining what good implementation
engineering looks like." Four defects found in `main`'s
implementation-role prompts were confirmed: mechanism over outcome; a
ledger of incidents in place of stated principle; done without effect;
the check held inside the maker's own prompt.

**Pressure on a principle in force (exchange 4).** "We need to take
care with delivery-verified. It could result in a lot of bottlenecks
and extra work if it is dogmatic and put in the wrong place. The term
'running system' itself is problematic when you are talking about
libraries or non-server products. The scenario can close when the
implementer shows it as complete through passing scenarios but the PM
is ultimately responsible for whether the delivered feature meets the
user need." The conflict with the principle's second statement was
named rather than smoothed. The authority split it out: "split our
[out] the principle vs definition of good", and directed the PM's
accountability into the role: "Write the accountability into the
lead-pm role."

**Second reframing (exchange 7), the one that set the bet.** "This the
build process and roles, not specifically the lead shop. We're
handling builds in the lead shop by defining the missing
implementation process and allowing the lead shop to do
implementation." With it, both lead-shop-special-case shapes from
exchange 1 dissolved: there is one implementation process, and the
lead shop is permitted to execute it on what it owns.

**A precision pass on the no-gos (exchange 8).** The authority
challenged "no second home for a rendering or install" as open to
interpretation. It was withdrawn — residue of the lead-pm's own
exchange-2 error, and a settled agreement rather than a boundary —
and replaced by the boundary it gestured at. The same test failed two
others: the `main` no-go ("informs general shape only" is not
checkable) and the scenario-assignment no-go (read one way it fenced
out the very edit the bet needs). Both restated.

### The bet

Framing: the system defines no implementation process and no
implementation roles, so the build activity belongs to no process and
no stated definition of good governs it; the lead shop's own
undefined builds exposed it. For whom: every shop that implements,
Bounded Context and lead alike, and the authority reading cost per
initiative; measure — scenarios built through a defined
implementation process, now 0, target every scenario of the next
assigned feature with its cost on an initiative. Appetite: two
working sessions — one for the definition of good for implementation
engineering and the two implementation roles, one for the process,
the lead shop's permission, and one proof run — placed in Phase 2
above the unstarted typedef-rendering batch. Six no-gos, as corrected
at exchange 8.

Accepted along the way: brief-030 ask 1's six sections and two rules
become required content in the role-definition typedef inside this
bet; the typedef today screens form alone. cold-reviewer, researcher
and router do not carry those sections and are recorded as debt.

### Run note

The `engage` step's first run at exchange 4 ended on a Fable rate

was sound but its re-put bet statement regressed to the pre-exchange-7
lead-shop framing and cut the accepted appetite from two sessions to

in the anchor's report comments.
