## 2. Enabler recommendations received

Two recommendations from the solutions architect role, recorded in
the initiative's history at v3 and priced in the checked decision
record [adr-2026-09-07-coordinator-role](../decisions/adr-2026-09-07-coordinator-role.md)
(v3, §3), and four candidates the same record names at its v1 as
"candidates for their own runs".

- **The router role definition** (the architect's R5; the ADR's first
  consequence). **Placed inside item 1**, as the first thing its
  feature produces. Reason: the role-definition typedef gives a role's
  authoring to the first process that needs it, and no run has a
  runner until the role is defined; a separate item would order a
  definition ahead of the outcome it exists for and outside the
  appetite's one session.
- **Agent steps return their declared outputs in a parseable form**
  (the architect's R3; the ADR's consequence "Agent outputs become
  parseable"; the designer's line that the return names the outputs
  as the step declares them). **Placed inside item 1, ahead of the
  run.** Reason: the first run branches on a typed output
  (`review.verdict`), so the run is not end to end without it; it
  changes no process definition, so the initiative's second no-go —
  no change to a process definition beyond what a run needs — does
  not bar it; the ADR prices it as one compiler change and a
  re-rendering, within the appetite. How it is done — the compiler
  line the architect names — is the maker's.
- **The router's tool list and model tier.** Declined as an item: a
  how, decided at item 1's feature make, as the ADR says.
- **A CEL evaluator tool.** Declined: its trigger — the first run
  mis-reading a condition (ADR §4) — has not fired; it enters a
  superseding order if it does.
- **A runner as the shopsystem's engine.** Declined: the initiative's
  first no-go (no code runner), and the migration review's question
  (req-2026-09-06-migration-review), not a requirement in any framed
  outcome.
- **An `integration-strategy` value for the adr typedef's `right`.**
  Declined: a typedef gap, the owner's definition change; it serves no
  framed outcome.

## 3. The order

**Item 1 — init-process-runner: one process run end to end by the
router (feature-to-be).**

- **Framing served:** the planned initiative
  [init-process-runner](../initiatives/init-process-runner.md)
  (planned, v6; a sub-initiative of init-run-efficiency; the
  authority's bet of 2026-09-07). Problem: the process definitions
  draw runtime, agent, and human steps, but nothing runs them — the
  lead-pm runs them by hand in one long context. Outcome: a process
  definition runs itself, and whoever moves the run carries only the
  step it is on. Measure: context tokens processed by whoever moves
  the run, per delivered feature — now 32M, target under 1M. That
  measure is one component of the parent init-run-efficiency's cost
  per delivered feature (42M to under 5M); this item moves the
  parent's measure by that component. Appetite: one session, one run
  end to end, measured. The decision the bet
  rests on stands checked: the ADR linked in §2. The two placed
  enablers of §2 are within this item.
- **Owning context:** none — lead-shop-internal. The ruling followed
  is the initiative's Decomposition section, the solutions architect
  role's attached ruling, screened and bet on: no Bounded Context is
  touched; the runner role, its rendering, and any compiler change sit
  in the lead shop's tree; no contract exists on this branch;
  cross-context flow none. Not a cross-context item; no escalation
  applies.
- **Readiness (first untaken item):** **not ready.** No feature exists
  — the initiative's Features section reads "None yet." It waits on
  the feature's authoring in the feature-authoring process and its
  pass through the PO output check.

No other items. Nothing else was declined: the only planned initiative
is placed, every active initiative's features are taken up, and no
other requirement has reached this role.
